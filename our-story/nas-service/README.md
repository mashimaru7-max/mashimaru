# 우리라는 이야기 · NAS 관리 API v2

기존 `nas-photo-test`를 교체하지 않는 별도 서비스다. 기본 compose는 사진을 읽기 전용으로 연결하고, 가족 공통 설정·사진 목록·미리보기 캐시를 별도 영구 볼륨 `/settings`에 저장한다. 업로드·휴지통을 활성화하려면 사용자의 NAS 쓰기 권한 변경 승인이 필요하다.

## 변경 이유와 영향

기존 사진 API는 조회만 지원한다. 웹페이지 버튼만으로 업로드/삭제를 구현할 수 없다. 새 컨테이너 `our-story-api`와 별도 터널 `our-story-tunnel`을 추가한다. 기존 서버·터널은 중단하거나 변경하지 않는다. 새 Quick Tunnel 주소를 웹의 연결 설정에 입력하면 기존 토큰을 재사용할 수 있다.

쓰기 활성화 시 `/volume1/photo`의 읽기 전용 마운트를 새 컨테이너에 한해서 읽기/쓰기로 바꾼다. 사진 업로드는 선택한 기존 폴더에 새 파일을 추가한다. 같은 이름은 덮어쓰지 않는다. 삭제 요청은 선택한 파일을 `/volume1/photo/.our-story-trash/<id>/photo`로 이동한다. 원래 경로와 삭제 시각은 같은 비공개 폴더의 `metadata.json`에 기록한다. 휴지통은 일반 갤러리에 표시하지 않고 자동으로 비우지 않는다. 원본 파일 내용과 EXIF는 바꾸지 않는다. 썸네일은 별도 설정 볼륨에 캐시하며 원본에 쓰지 않는다. 복원은 원래 폴더에 같은 이름이 있으면 중단한다. 영구삭제는 아래 명시적 휴지통 선택 절차만 제공한다.

기존 토큰은 새 쓰기 API에도 접근할 수 있게 되므로 토큰을 아는 사람은 쓰기 권한을 갖는다. 가족별 로그인과 권한은 아직 없으며, NAS 관리자는 나중에 별도 관리 토큰으로 분리할 수 있다. CORS는 페이지 origin을 검사하지만 토큰 유출에 대한 접근 통제 대체 수단은 아니다. 실제 `.env`, 토큰, 사진은 Git에 포함하면 안 된다.

## 휴대폰에서도 준비할 수 있는 설치 자료

- 소스 묶음: `../downloads/our-story-nas-service.zip` (비밀 없음)
- GitHub 저장소 → Actions → **Build Our Story NAS service image** → 완료된 실행의 Artifacts → `our-story-nas-amd64` 다운로드. ZIP을 풀면 Docker 가져오기용 `our-story-nas-amd64.tar`가 있다. 유효기간 7일. 필요하면 Run workflow로 다시 만든다. DS218+용 linux/amd64 이미지이며 NAS에는 자동 설치하지 않는다.
- Docker 이미지 실제 빌드 여부는 해당 Actions 실행 결과를 확인한다. DSM 7.1.1 설치/권한 호환성은 실제 NAS에서 별도 확인해야 한다.

## DSM Docker GUI로 별도 컨테이너 추가 (승인 이후)

1. 먼저 실제 `/photo` 공유 폴더 백업/스냅샷 상태와 사진 권한이 있는 DSM 계정 UID/GID를 확인한다. 예시 `1024:100`은 설치마다 다르며 관리자/root 권한으로 우회하지 않는다.
2. File Station에 tar 파일 업로드 → Docker → 이미지 → 추가 → 파일에서 추가로 가져온다. 기존 Python/cloudflared 컨테이너는 유지한다.
3. 새 Docker 브리지 네트워크 `our-story-net` 생성. `our-story-nas:2` 이미지로 **새 컨테이너** `our-story-api` 생성. 새 네트워크에만 연결한다. 호스트 네트워크·공개 호스트 포트는 사용하지 않는다.
4. 볼륨에 실제 `photo` 공유 폴더를 `/photos`로 추가하고 **우선 읽기 전용**을 체크한다. 사진 폴더와 별도로 영구 설정 폴더를 `/settings`에 읽기/쓰기로 마운트한다. 이 폴더는 컨테이너 사용자 UID/GID가 쓸 수 있어야 하며 사진 공유 폴더 안에 만들지 않는다. 환경 변수 `SETTINGS_ROOT=/settings`를 추가한다. 환경 변수 `NAS_TOKEN`에 기존 조회 토큰, `ALLOWED_ORIGIN=https://mashimaru7-max.github.io`, `ENABLE_WRITES=0` 설정. 비밀을 웹 코드나 GitHub Actions에 입력하지 않는다. 기본 이미지 사용자는 `1024:100`이므로 실제 계정이 다르면 적절한 사용자로 컨테이너를 구성해야 한다. GUI에서 사용자 지정이 어려우면 아래 compose 경로를 사용한다.
5. 이미 내려받은 공식 `cloudflare/cloudflared` 이미지로 **새 컨테이너** `our-story-tunnel` 생성. `our-story-net`에 연결. 명령: `tunnel --no-autoupdate --url http://our-story-api:8000`. 네트워크에서 이름 해석이 되는지 로그 확인. 기존 터널은 수정하지 않는다.
6. 새 터널 로그의 HTTPS 주소를 웹 연결 설정에 입력. 토큰 칸은 비워 저장된 토큰을 재사용한다. 목록/썸네일/다운로드부터 확인한다. Quick Tunnel 주소는 재시작 시 바뀔 수 있다.
7. **쓰기 승인 후에만** 새 API 컨테이너의 사진 볼륨을 읽기/쓰기로 바꾸고 `ENABLE_WRITES=1` 설정. DSM에서 컨테이너 재생성이 필요한 경우 새 컨테이너만 재생성한다. 먼저 별도 시험 폴더에서 사진 한 장 업로드 → 휴지통 이동 → 복원을 검증한다. 권한이 안 맞으면 서버가 403을 반환하며 원본 권한을 임의로 완화하지 않는다.

이 단계는 실제 NAS 화면을 확인하며 진행해야 하며, 이 문서는 설치 완료를 의미하지 않는다.

## Compose 사용 가능 시

로컬 NAS 전용 폴더에서 `.env.example`을 `.env`로 복사하고 토큰과 실제 UID/GID 입력. 읽기 전용 실행:

```sh
docker-compose -p our-story -f docker-compose.yml up -d
```

쓰기 승인 이후 실행:

```sh
docker-compose -p our-story -f docker-compose.yml -f docker-compose.write.yml up -d
```

빌드된 이미지를 Docker GUI로 가져온 경우 이미지를 재사용한다. 서버 코드는 원본 프로젝트를 참조하지 않는다. 이 예시는 DS218+의 실제 볼륨이 `/volume1/photo`인 경우이며 경로는 실제 환경에 맞춰야 한다. 롤백 시 새 컨테이너/터널만 정지하고 원래 웹 연결 주소로 돌아간다. 휴지통 폴더는 지우지 말고 필요한 파일을 먼저 복원한다.

## API 계약

모든 요청은 `Authorization: Bearer ...`, 정확한 `Origin` 필요. OPTIONS만 토큰 없이 허용 origin 검사. 토큰은 URL에 넣지 않는다. 쿠키·공개 정적 사진 URL·인증 없는 썸네일 없음.

| 경로 | 동작 |
| --- | --- |
| GET `/api/capabilities` | v2 지원 기능과 쓰기 권한 표시 |
| GET `/api/settings` | 같은 NAS의 공통 앨범 폴더·이름 규칙·대표사진과 revision |
| POST `/api/settings` | JSON `{revision, albums?, home?}`, 인증 후 설정만 원자적 저장, 이전 revision은 409 |
| GET `/api/list?path=&offset=0` | 100개 단위 목록, revision 포함 |
| GET `/api/image?path=...` | 원본 미리보기, 최대 15MB |
| GET `/api/thumbnail?path=...` | 최대 1600px JPEG, EXIF 제거, Pillow가 지원하는 형식만 |
| GET `/api/download?path=...` | 원본 다운로드, 최대 128MB |
| POST `/api/upload?path=...&name=...` | raw binary, 파일당 64MB, 지원 사진 확장자·서명/디코딩 검사 |
| POST `/api/trash` | JSON `{path, revision}`, 휴지통 이동 |
| GET `/api/trash` | 휴지통 목록 최대 1000개 |
| POST `/api/restore` | JSON `{id}`, 원래 위치로 복원 |

심볼릭 링크·숨김 폴더·상위 경로·URL 이중 디코딩 경로를 거부한다. 디렉터리 파일 디스크립터를 기준으로 접근한다. 쓰기 작업은 서버 내 잠금으로 직렬화하며 외부 Synology Photos/SMB의 동시 편집까지 잠그지는 못한다. 그 외부 프로그램과 같은 파일을 동시에 변경하지 말아야 한다. 프로세스 중단 시 숨김 업로드 임시 파일 또는 미완성 휴지통 메타데이터가 남을 수 있으며 자동 정리/영구 삭제하지 않는다. 운영 전 백업과 장애 복구 점검이 필요하다.

썸네일 동시 변환 2개, HTTP 요청 최대 8개. HEIC/HEIF 코덱 플러그인은 포함하지 않아 해당 형식의 썸네일은 실패할 수 있다. 파일 자체 다운로드는 지원한다. 영상 자동 변환·대량 ZIP·GPS 자동 분류·가족별 인증·고정 터널은 구현 범위 밖이다.

## 검증

Python 3.12 이상/Linux와 Pillow 13.0.0 대상. 현재 임시 디렉터리 HTTP 시험 14개 통과. 실제 NAS·DSM 설치와 네트워크는 미검증. 실행:

```sh
python -m unittest discover -s our-story/tests -p test_nas_service.py -v
```

## 가족 공통 설정 업데이트

이 버전부터 홈/여행/다온/라온/함께 폴더 연결, 이름으로 모으기 규칙, 직접 고른 홈 대표사진을 NAS에 공통 저장한다. 같은 NAS 주소·토큰으로 접속하면 가족 모두 같은 설정을 사용한다. 토큰 자체는 각 브라우저의 기존 암호화 저장에 남는다. 사진 쓰기 기능을 켜지 않아도 공통 설정을 저장할 수 있다. 설정에는 사진 경로와 이름만 있고 사진 원본/토큰/비밀번호는 없다. 토큰을 가진 가족은 공통 설정도 수정할 수 있다.

1. 업데이트된 소스 ZIP 또는 새 Actions 이미지로 **our-story-api만** 교체한다. 기존 `nas-photo-test`는 변경하지 않는다.
2. Compose는 새 `our-story-settings` 영구 볼륨을 `/settings`에 연결한다. 기본 이미지 UID/GID는 1024:100이다. `NAS_UID`/`NAS_GID`를 바꿨다면 설정 볼륨도 그 사용자에게 쓰기 권한이 있어야 한다. GUI 설치는 위의 별도 영구 설정 폴더를 사용한다. 컨테이너 내부 폴더만 사용하면 재생성 시 설정이 사라진다.
3. Compose로 소스 빌드 시 `docker-compose -p our-story -f docker-compose.yml up -d --build our-story-api` 실행. 사진 쓰기 기능을 이미 사용 중이면 기존 write override도 동일하게 포함한다. 설정 볼륨을 삭제하는 `down -v`는 사용하지 않는다.
4. 기존 설정이 있는 기기에서 먼저 새 서버에 연결한다. 동일한 API 주소이고 서버가 처음 설정되는 경우 기존 암호화 앨범/대표사진을 자동 이관한다. **터널 주소가 바뀌었다면 이전 주소로 저장된 설정은 자동 이관하지 않는다.** 새 주소에서 폴더/이름 규칙을 한 번 다시 저장하면 이후 가족에게 공유된다.
5. 다른 브라우저에서 같은 NAS 주소·토큰으로 접속해 공통 앨범과 대표사진을 확인한다. 변경사항은 새 접속, 창 포커스 복귀 또는 최대 15초 간격 확인으로 반영된다. 탭/연도 필터 등 현재 탐색 상태는 기기마다 다를 수 있다.

이미 가족 설정이 있는 NAS에는 새 기기의 예전/빈 설정을 자동 덮어쓰지 않는다. 동시에 다른 항목을 수정하면 revision 충돌 후 최신 설정을 읽어 해당 항목만 다시 저장한다. 같은 항목의 편집은 마지막 성공 저장을 따른다. 서버가 구버전이면 사진 조회는 유지하고 업데이트 안내를 표시하며, 공통 저장 성공으로 표시하지 않는다. 실제 NAS 배포/권한 및 가족 기기 연결은 별도 검증이 필요하다. 여행·성장 **예시 이야기 기록**은 여전히 메모리 체험이며 이 설정 동기화 범위에 포함되지 않는다.


## 1단계: 가족 공통 사진 목록과 미리보기 저장 (2026-11-13)

- `/settings/settings.json`: 기존 가족 대표사진·폴더·이름 규칙 유지.
- `/settings/archive.sqlite3`: 공통 사진 경로·파일 revision·연도 폴더·정렬·탐색 진행 상태. 원본 사진과 토큰을 DB에 복제하지 않는다.
- `/settings/thumbnails`: 필요할 때 생성하는 JPEG 미리보기. 원본 revision이 바뀌면 다시 생성하며, 최근 사용 기준으로 약 512 MiB 이내를 유지한다. 캐시 삭제는 원본에 영향을 주지 않는다.
- 인증된 `POST /api/album-index`만 사용한다. 앨범 key/year/refresh만 받으며 연결 규칙은 서버 공통 설정에서 읽는다. `GET /api/capabilities`의 `sharedArchive:true`로 구버전과 구분한다.
- 표시 순서는 연도 폴더 내림차순 → 전체 경로의 고정 순서다. 촬영일·인물·나이를 추정하지 않는다. 서버 전체 목록에서 화면용 12장(홈은 8장)을 가져오며, 갤러리의 전체 사진 탐색 제한과 무관하다.
- 최초 탐색은 공통 DB에 저장된 사진부터 고정 정렬로 표시한다. 최초 탐색 중에는 사진이 추가되면서 표시 순서가 갱신될 수 있다. 완료 목록이 이미 있으면 재탐색 완료까지 그 목록을 유지한다. 요청마다 최대 20개 폴더 목록 페이지/약 1.5초씩 처리하고 진행 상태를 저장한다. 화면이 열려 있으면 준비 중 5초 간격으로 이어서 처리하며 닫았다가 다시 열어도 이어진다. 화면에는 확인한 목록 수·발견 사진 수·남은 작업 수를 표시하고, 갱신 오류도 숨기지 않는다. 열린 화면은 평상시 60초 간격으로 확인하며, 완료 목록은 5분이 지나면 재탐색한다. 상시 백그라운드 감시는 아니다.
- 재탐색 중에는 기존 완료 목록을 유지하고 완료 시 전환한다. 읽기 오류가 있는 재탐색은 이전 정상 목록을 보존한다. 첫 탐색에 오류가 있으면 읽을 수 있었던 범위와 오류 안내가 표시된다. 탐색 깊이 32/대기 폴더 10,000/연결 폴더 표시 5,000을 넘으면 오류 수로 알린다.
- 새 NAS 주소에서도 같은 설정 볼륨을 사용하면 공통 설정을 재사용한다. 단, 새 주소와 토큰으로 각 기기의 연결 인증은 필요하다. 예전 기기 설정 최초 이관은 동일 주소에서만 자동 수행한다.

### NAS 적용 영향과 순서

이번 단계는 `docker-compose.yml` 단독 사용: `ENABLE_WRITES=0`, `/volume1/photo:/photos:ro`를 유지한다. 쓰기 override를 추가하지 않는다. 기존 사진 API·터널은 그대로 두고 별도 API/터널을 설치한다. 추가되는 쓰기는 새 컨테이너의 `/settings` 볼륨뿐이다. 이 NAS 변경을 사용자에게 설명하고 승인받은 뒤 적용한다.

새 이미지에는 공통 설정·목록·캐시가 모두 포함된다. 기존 새 API를 이미 설치했다면 `/settings` 볼륨을 유지하며 이미지/컨테이너만 업데이트한다. `down -v`는 실행하지 않는다. 같은 설정 볼륨을 여러 API 컨테이너에 동시에 연결하지 않는다. 롤백은 새 컨테이너만 중지하고 기존 API를 계속 사용한다. `/settings`는 컨테이너를 중지한 상태로 백업한다.

실기기 확인은 ① 기존 설정 기기에서 연결 및 목록 준비 완료 ② 다른 브라우저에서 같은 표지·순서 확인 ③ 새 API 컨테이너 재시작 후 유지 ④ NAS에 새 사진을 넣은 뒤 ‘새로 불러오기’로 갱신, 네 가지면 된다. 이 저장 범위는 사진 연결과 목록이며, 예시 여행/성장 이야기의 영구 저장이나 로그인은 포함하지 않는다.


### 기존 v2 이미지에 코드만 적용하기

`downloads/our-story-index-fix.zip`에는 수정된 `server.py` 한 파일만 있다. NAS의 별도 `docker/our-story/hotfix` 폴더에 압축을 풀고, 새 API 컨테이너를 중지한 뒤 **파일 추가**로 그 파일을 `/app/server.py`에 읽기 전용 마운트한다. 기존 `/photos`, `/settings`, 환경 변수, 네트워크는 유지한다. API만 재시작하며 터널은 재시작하지 않는다. 계정 설정 이후에는 파일 마운트를 제거해 로그인 미지원 이미지로 되돌리지 않는다. 복구 시 로그인 지원 코드와 기존 설정 볼륨을 유지한다. 기존 API나 사진 파일에는 적용하지 않는다.


## 방문마다 사진 랜덤 표시

공통 설정과 전체 사진 인덱스는 가족이 공유하되, 각 방문의 표시 사진은 달라진다. 웹은 페이지 진입/아이 선택 변경/명시적 ‘새로 불러오기’에 128-bit 무작위 seed를 만든다. 같은 페이지의 일반 재렌더와 백그라운드 폴링에서는 seed를 유지한다. SQL에서 전체 대상 목록을 seed+경로의 SHA-256 순으로 정렬해 최대 12장을 뽑으므로, 기존 미리보기 12장만 섞는 방식이 아니다. 같은 목록·seed에서는 같은 결과다. 표본이 적으면 재방문해도 같은 사진이 나올 수 있으며 반복 금지는 아니다. 새 사진 발견/인덱스 갱신으로 대상 목록 자체가 바뀌는 경우 표시는 달라질 수 있다.

직접 지정한 홈 대표사진은 고정한다. 자동 홈 대표사진·앨범·홈의 앨범 표지는 방문 seed를 따른다. 연도 필터는 그 연도의 대상 사진 안에서만 적용된다. 사진 목록을 읽는 기본 API는 seed가 없으면 기존 고정 정렬을 유지한다. `randomAlbums:true` 기능 응답이 없는 구버전 NAS에는 seed를 전송하지 않고 업데이트 안내를 표시한다. 기존 `/settings` 데이터 변경이나 사진 권한 변경은 필요 없다.

기존 hotfix 파일 마운트가 있다면 API를 중지하고 `downloads/our-story-random-albums.zip`의 `server.py`로 NAS의 `hotfix/server.py`만 교체한 뒤 API를 재시작한다. 터널은 유지한다.


## 가족 공용 로그인: 오니둥이

### 적용

1. 새 API 컨테이너만 중지하고 `downloads/our-story-family-login.zip`의 `server.py`를 NAS의 기존 `docker/our-story/hotfix/server.py`에 덮어쓴다. 기존 파일 마운트 `/app/server.py`와 `/settings` 볼륨, 토큰 환경 변수, 사진 읽기 전용 마운트는 유지한다. API를 다시 시작한다. 터널/기존 사진 테스트 API는 변경하지 않는다.
2. 기존 연결이 기억된 기기에서 웹을 새로고침하고 프로필의 연결 설정을 연다. `가족 공용 로그인 만들기`에 새 비밀번호와 확인을 입력한다. 아이디는 `오니둥이`, 비밀번호는 10~128자이며 채팅·Git·NAS 환경 변수에 입력하지 않는다. 최초 계정 생성은 기존 NAS 토큰으로 인증된 기기에서만 허용된다.
3. 설정 성공 시 이 기기도 공용 계정으로 다시 로그인한다. 이후 새 API에서는 기존 토큰으로 사진·설정에 접근할 수 없다. 다른 기기의 이전 토큰 연결도 다시 로그인해야 한다. 기존 별도 사진 테스트 API는 보존하므로 그 서비스의 토큰 정책은 바뀌지 않는다.
4. 다른 기기는 웹에서 `오니둥이`와 설정한 비밀번호만 입력하고 로그인 유지를 선택한다. NAS 주소는 공개 `family-config.mjs`에서 제공하며 비밀이 아니다. 현재 Quick Tunnel은 임시 주소이므로 터널 주소가 바뀌면 관리자가 이 설정 파일을 갱신해야 한다. 고정 도메인 연결을 완료한 것은 아니다.

### 저장과 검증

- 서버는 `/settings/auth.sqlite3`에 scrypt(N=131072,r=8,p=1,16-byte 무작위 salt)의 비밀번호 해시와 세션 토큰의 SHA-256만 저장한다. 평문 비밀번호·세션은 DB나 로그에 저장하지 않는다.
- 세션은 무작위 256-bit이며 30일 만료, 최대 20개 기기 세션을 유지한다. API 재시작 뒤에도 유효하며 로그아웃 시 해당 세션을 서버에서 폐기한다. 클라이언트는 기존 AES-GCM IndexedDB 저장을 사용하고 비밀번호는 저장하지 않는다. 로그인 유지 체크를 해제하면 화면을 닫을 때 로컬 인증을 지우고 서버에 세션 폐기를 요청한다. 브라우저 종료 시 요청 완료는 보장되지 않으며 남은 세션은 만료 시 거부된다.
- 모든 사진/목록/설정 API가 서버에서 세션을 검사한다. 인증을 숨겨진 UI나 공개 URL의 비밀성에 맡기지 않는다. 쿠키 대신 Authorization 헤더를 사용해 GitHub Pages와 NAS 사이의 제3자 쿠키 제한을 피한다. 허용 Origin은 기존 GitHub Pages 하나로 유지한다.
- 로그인 실패는 60초간 10회까지 허용하며 이후 429, 비밀번호 해시 계산 동시성은 1이다. 계정 생성 후 재설정/비밀번호 변경 기능은 아직 제공하지 않는다. 공용 계정이므로 가족별 작성자·권한 구분도 없다.
- 비밀번호 설정 전에는 기존 토큰 모드를 유지한다. 이미 설정된 계정은 토큰이나 로그인 화면으로 덮어쓰지 못한다. 관리자용 접속 설정은 접힌 영역에 유지한다.
- 실제 NAS 확인은 최초 설정 → 다른 브라우저 로그인 → 사진/공통 설정 확인 → 한 기기 로그아웃 및 재로그인으로 제한한다. 테스트 사진을 업로드하거나 원본을 이동할 필요가 없다.

인증 DB를 만든 후에는 로그인 지원 이전 코드로 되돌리면 안 된다. 이전 코드는 기존 토큰을 다시 허용하기 때문이다. 장애 시 새 API/터널을 중지하고 설정 볼륨을 보존한 뒤 로그인 지원 버전으로 복구한다. 인증 DB와 설정 볼륨 백업은 개인정보로 취급한다.


## 성장 기록 영구 저장 (2026-11-14)

### 설치와 첫 확인

새 API만 중지하고 `downloads/our-story-growth-records.zip`의 `server.py`를 기존 NAS `docker/our-story/hotfix/server.py`에 덮어쓴 뒤 다시 실행한다. `/settings`와 기존 로그인 DB·설정·미리보기는 그대로 유지한다. 사진 마운트 `/photos`는 **읽기 전용**, `ENABLE_WRITES=0`을 유지한다. 기록 저장을 위해 사진 쓰기를 활성화하지 않는다. 터널과 기존 사진 테스트 컨테이너도 변경하지 않는다.

웹 새로고침 → 로그인 → 성장앨범의 다온/라온에서 기록 남기기. 최초 DB는 실제 기록 조회/저장 시 `/settings/journal.sqlite3`에 생성된다. DB 파일은 컨테이너 사용자 소유, 모드 0600이다. 외부에 공개된 GitHub에는 사용자 기록·사진·인증 DB를 포함하지 않는다.

### 데이터와 API

- 공통: 대상 아이, 종류, 날짜, 선택한 작성자 표시, 서버 생성/수정 시각, UUID, 수정 revision.
- 일기: 제목·자유 주제·본문·기억할 마음. 아이의 말: 인용문·상대·상황. 편지: 본문·다시 읽을 날짜. 측정: 키/몸무게 중 하나 이상·측정 메모. 작성자 표시는 공용 계정 내에서 선택한 이름이며 개별 사용자 인증/감사 기록을 의미하지 않는다.
- 사진은 기록당 최대 6장. NAS 파일 경로와 revision만 보관한다. 저장 시 해당 파일이 존재하고 revision이 일치하는지 서버에서 읽기 전용으로 확인한다. 원본을 복제·이동·수정하지 않는다. NAS 외부에서 사진을 이동/변경하면 기록은 유지되지만 해당 사진을 다시 연결해야 할 수 있다. 영상과 실제 여행 기록 ID 연결은 아직 지원하지 않는다.
- 인증된 GET `/api/journal`: target, kind, year, q, trash(0/1), offset; 10개씩 조회. id 단독 조회도 지원. 정렬은 기록 날짜 내림차순 → UUID 내림차순.
- 인증된 POST `/api/journal`: action(save/trash/restore), id, revision, record(save만). JSON 본문 최대 128 KiB. 종류별 필드·범위·실제 달력 날짜·첨부 경로/파일을 서버가 검증한다. 최초 계정 생성 전의 구 토큰 모드로는 기록 API를 사용할 수 없다.
- create는 클라이언트 생성 UUID를 사용한다. 저장 응답 유실 후 동일 UUID/동일 내용으로 재시도하면 중복 기록을 만들지 않는다. 수정·휴지통·복원은 BEGIN IMMEDIATE와 revision으로 충돌 시 409를 반환한다. 충돌을 자동 덮어쓰기하지 않는다. 기록 종류와 대상 변경은 이번 버전에 허용하지 않는다.
- 휴지통은 DB의 삭제 표시만 바꾸며 영구 삭제 API가 없다. 휴지통 이동·복원은 연결한 원본 사진을 건드리지 않는다.
- 로그인한 다른 기기는 페이지 진입/창 복귀/30초 간격에 최신 목록을 읽는다. 작성 중에는 목록 자동 갱신을 멈춘다. 검색·종류·연도 필터와 더 보기를 제공한다. 저장 실패/충돌 때 폼 입력을 유지하며, 로그인 종료 시에는 화면의 개인 기록을 지운다. 초안은 브라우저 영구 저장소에 저장하지 않는다.

### 별도 백업

화면의 ‘기록 DB 백업’은 인증된 GET `/api/journal-backup`을 사용한다. sqlite backup API로 일관된 스냅샷을 별도 임시 파일(0600)에 만들고 스트리밍 다운로드 후 제거한다. 다운로드 최대 64 MiB. 두 아이/함께 대상과 휴지통을 포함한 기록 DB 전체이며 인증 정보·사진 원본·앨범 설정은 포함하지 않는다. 백업 파일은 비공개로 보관한다. 백업 복원/예약 백업 UI는 아직 없고, 관리자 승인 후 API를 중지한 상태에서 별도 복원해야 한다. 컨테이너 업데이트 시 DB는 보존되며 설정 볼륨 삭제 금지.

실제 NAS의 최소 검증: ① 기록 하나 저장 후 새로고침 ② 다른 기기에서 같은 기록 확인 ③ 수정 후 휴지통 이동/복원 ④ 기록 DB 백업 다운로드. 사진 첨부는 선택이며 실제 사진 업로드/삭제 시험은 필요 없다.


## 갤러리 사진 쓰기와 폴더 정리 (2026-11-14)

### 적용 범위와 NAS 설정

이 단계는 사용자가 승인한 사진 업로드·휴지통·복원과 폴더 생성/이름 변경/이동을 활성화한다. 새 API 컨테이너만 중지하고 `downloads/our-story-gallery-management.zip`의 `server.py`를 기존 `docker/our-story/hotfix/server.py`에 덮어쓴다. 새 API의 `/photos` 마운트만 읽기/쓰기로 바꾸고 `ENABLE_WRITES=1`로 변경한 뒤 다시 시작한다. 기존 `/settings`·로그인·터널·기존 사진 테스트 API는 유지한다. 다른 컨테이너에 사진 쓰기를 추가하지 않는다.

컨테이너 UID 1024가 실제 작업 폴더를 쓸 수 있는 NAS ACL도 필요하다. 마운트 변경만으로 NAS 권한을 우회하지 않는다. 권한 오류가 확인되면 해당 폴더의 admin(현재 설치에서 UID 1024) 읽기·쓰기를 확인한다. Everyone 쓰기/관리 권한 부여나 사진 전체 소유권 변경을 요구하지 않는다. 실제 사진을 정리하기 전에 별도 `우리웹테스트` 폴더와 임시 사진 한 장으로 확인한다.

### 기능과 제한

- 기존 다중 사진 업로드(파일당 64 MiB), 원본 다운로드(128 MiB), 사진 휴지통·복원을 유지한다. 같은 이름은 덮어쓰지 않으며 업로드 중단 시 미완료 임시 파일만 제거한다. 완료된 업로드는 유지한다.
- ‘새 폴더’: 현재 폴더에 전용 mkdir 호출. ‘사진·폴더 정리’: 현재 로딩한 목록에서 항목 선택 후 새 이름·목적지 지정. 폴더 브라우저는 하위 폴더만 보여주고 경로/이전·다음 목록을 제공한다.
- POST `/api/files`: mkdir(action,parent,name) 또는 move(action,path,revision,destination,name,operationId). 이동은 가족 로그인 설정 후 인증된 세션에서만 허용한다. 원본 CAS revision, 파일 형식 확장자 유지, 폴더의 자기 하위 이동 금지, 원본 루트 조작 금지, 경로 검증을 서버에서 수행한다.
- Linux renameat2(RENAME_NOREPLACE)만 사용한다. 미지원 커널/파일시스템/다른 볼륨 간 이동에는 501로 거부하며, 덮어쓸 수 있는 일반 rename이나 복사 후 삭제로 대체하지 않는다. 새 API는 쓰기 모드에서 서비스 전용 `.our-story-trash` 안의 임시 빈 폴더만으로 충돌 거부/이동/복원을 점검한다. 안전 이동·복원을 확인할 수 없으면 사진 휴지통 기능도 활성화하지 않는다. 이 점검은 원본 사진을 조작하지 않는다.
- 숨김 폴더·@로 시작하는 NAS 관리 폴더·#recycle·#snapshot·심볼릭 링크 경유 경로는 조작하지 않는다. 대량 위치 변경은 제공하지 않는다. 영상 관리는 아래 확장 기능을 따른다. 폴더째 휴지통과 선택 일괄 휴지통은 아래 확장 기능으로 지원한다. 폴더 이동은 선택한 폴더 전체 내용을 같은 파일시스템 안에서 옮긴다.

### 연결 유지와 복구

이동·이름 변경 시 고정 앨범 경로, 이름 규칙의 검색 root, 직접 선택한 홈 대표사진 경로/이름, 활성/휴지통 성장 기록의 사진 참조를 함께 갱신한다. 이름 규칙의 text는 자동 변경하지 않는다. 따라서 폴더 이름을 바꾸면 규칙과 일치하지 않아 해당 앨범에서 빠질 수 있으며 확인 화면에 안내한다. Synology Photos의 자체 앨범/공유 링크 보존까지 보장하는 기능은 아니다. 재색인이 발생할 수 있으므로 실제 NAS에서 별도 확인하고 다른 앱/SMB와 동시에 정리하지 않는다.

파일의 inode/크기/mtime과 저장된 revision을 확인한 참조만 새 revision으로 연결한다. 이미 다른 사진으로 교체된 참조는 새 위치로 경로만 갱신하고 이전 revision을 유지해 잘못된 사진이 표시되지 않게 한다. 사진 휴지통 메타에는 원래 revision과 파일 식별 정보를 보관하며 복원 시 같은 파일임을 확인한 성장 기록 참조를 다시 맞춘다. 사진을 휴지통에 보관한 동안에는 해당 기록의 사진이 표시되지 않는다. 구버전에서 만든 휴지통 항목은 원본 복원은 가능하지만 참조 재연결 정보가 없으면 직접 다시 연결해야 할 수 있다.

`/settings/file-operations.sqlite3`(0600)에 이동 의도→실제 이동→메타데이터 갱신→완료 순으로 내역을 저장한다. 파일시스템과 JSON/SQLite는 단일 원자 트랜잭션이 아니므로, 서버 시작/다음 인증 요청에서 진행 중 작업을 멱등 복구한다. 이동이 시작되지 않았으면 취소하고, 목적지 inode가 일치하면 나머지 연결을 완료한다. 다른 앱이 파일을 바꾸어 위치를 확정할 수 없으면 503으로 메타데이터 작업을 멈추고 수동 확인을 요구한다. 모호한 파일을 자동 덮어쓰기/삭제/되돌리지 않는다. 완료/취소 내역은 본문 스냅샷을 제거하고 요청/결과 정보만 남긴다.

관련 쓰기 요청은 직렬화한다. 긴 업로드 전송은 기록 읽기·저장 잠금을 계속 잡지 않는다. 원본 사진 변경 후 파생 사진 목록 캐시만 초기화해 다음 접속에서 다시 모은다. 일반 사진 요청은 기존 인증·범위 검사를 유지한다. 메타데이터 계획은 연결 성장 기록 최대 1,000개 또는 약 16 MiB로 제한하고 초과 시 원본 변경 전에 413으로 거부한다.

### 실기기 최소 검증

1. `우리웹테스트`에서 하위 폴더 만들기, 사진 한 장 업로드 및 원본 다운로드 확인.
2. 사진을 휴지통으로 옮기고 복원해 다운로드 원본이 유지되는지 확인.
3. 테스트 폴더 이름/위치 변경 후 목록 확인. 연결한 테스트 성장 기록이 있으면 사진도 이어지는지 확인.
4. Synology Photos에서도 테스트 사진을 조회할 수 있는지 확인한 뒤 실제 폴더 정리를 시작한다.

이 절차는 실제 NAS에서 자동 수행되지 않았다. 코드 테스트는 모두 임시 폴더에서만 수행했다. 사진 원본과 설정/기록 볼륨을 별도로 백업하며, 진행 중 파일 작업이 있다면 API를 중지한 상태에서 설정 볼륨 전체와 사진 위치를 함께 보존한다. 예전 로그인 미지원 이미지로 원복하지 않는다.


## 선택 일괄 휴지통·폴더 전체 복원

`downloads/our-story-gallery-selection.zip`의 `server.py`로 기존 hotfix 파일을 교체하고 새 API만 재시작한다. 기존 `/photos:rw`, `ENABLE_WRITES=1`, `/settings`, 로그인과 터널은 유지한다.

갤러리 ‘선택하기’에서 사진/폴더를 체크하거나 현재 불러온 항목을 전체 선택한다. 아직 불러오지 않은 페이지는 자동 선택하지 않으며, 더 불러온 항목을 포함하려면 다시 전체 선택한다. 다른 폴더로 이동/로그아웃/갤러리 이탈 시 선택을 지운다. 선택된 항목은 경로와 그 시점의 revision을 유지해, 나중에 같은 이름으로 교체된 항목을 조용히 삭제하지 않는다. 변동된 항목은 목록에서 명시적으로 다시 선택해야 한다.

확인 화면은 사진 수·폴더 수·이름을 보여주고 폴더의 하위 내용 전체가 함께 휴지통으로 간다고 안내한다. 각 요청을 순서대로 처리하며 완료/확인 필요/미처리 수를 구분한다. ‘남은 작업 중지’는 현재 요청이 마무리된 뒤 다음 항목을 보내지 않는다. 권한/인증/네트워크/복구 오류에는 추가 요청을 중단하고, 개별 충돌이나 없는 항목은 다른 선택을 계속 처리한다. 연결이 끊긴 항목은 이미 완료됐을 수 있으므로 확인 필요로 표시하고 휴지통/목록을 확인하도록 한다.

폴더 휴지통 요청은 `/api/trash`의 `kind:folder`를 명시해야 하며 가족 로그인·사진 쓰기·안전 복원이 모두 확인되어야 한다. 루트·시스템 경로와 심볼릭 링크 경유는 기존대로 거부한다. 폴더 자체를 서비스 전용 휴지통으로 원자 이동하므로 하위 사진·영상·기타 파일의 바이트를 변경/필터링하지 않는다. 개별 영상 관리 기능을 추가한 것은 아니다. 휴지통 항목은 사진/폴더를 구분하며 같은 복원 버튼으로 되돌린다. 원래 위치에 폴더가 생겼으면 합치거나 덮어쓰지 않고 409로 보존한다. 상위 폴더가 없으면 먼저 상위 폴더를 복원해야 한다.

삭제 전에 기록에 연결된 사진의 식별 정보를 휴지통 메타에 저장하며, 폴더 복원 시 일치하는 성장 기록 참조를 다시 맞춘다. 이미 다른 파일로 교체된 참조를 새 사진으로 승인하지 않는다. 기록은 휴지통 이동 동안 그대로 남고 사진만 표시되지 않는다. 기존 고정 앨범/대표사진 경로도 삭제하지 않으므로 원래 위치로 복원하면 다시 조회한다. 참조 메타는 최대 2 MiB이며 기존 연결 기록 제한을 넘으면 원본 변경 전에 거부한다. 폴더 영구삭제는 아래 별도 확인 절차만 따른다.


## 선택 휴지통 영구삭제

`downloads/our-story-permanent-trash.zip`의 `server.py`를 기존 hotfix 파일에 덮어쓰고 API만 재시작한다. 기존 로그인, `/settings:rw`, `/photos:rw`, `ENABLE_WRITES=1`, 파일 마운트 및 터널은 유지한다. 사진 경로를 직접 삭제하는 API나 자동 휴지통 비우기는 없다.

휴지통에서 최대 50개 항목 선택 → 공용 비밀번호 재입력 → 하위 파일·폴더 수와 경로 확인 → 복원 불가 체크 → 영구삭제 실행. 비밀번호는 저장하지 않고 기존 scrypt 검증/시도 제한을 재사용한다. 틀린 비밀번호는 422로 현재 세션을 유지한다. 서버는 세션에 귀속된 120초 일회용 확인권을 발급하며, 확인 이후 파일 상태가 바뀌면 삭제 전에 거부한다. 확인권은 메모리만 사용하므로 API 재시작 후 재확인이 필요하다.

삭제 대상은 서비스 전용 휴지통의 명시적 UUID뿐이다. fd 기반 symlink-safe rmtree를 사용하고 내부 심볼릭 링크는 링크만 지운다. 다른 마운트와 특수 파일은 거부한다. 한 확인 요청의 점검 시간은 최대 30초, 항목당 100,000개 노드/깊이 64이며 초과 시 거부한다. 서버 사진 작업 잠금은 외부 SMB/DSM 편집을 잠그지 못하므로 같은 휴지통을 다른 앱에서 동시에 변경하지 않는다.

`/settings/permanent-trash.sqlite3`에 작업 의도를 기록한다. 재시작 시 물리 삭제를 자동 재개하지 않고, 이미 원본이 없어진 작업의 메타데이터 정리만 복구한다. 일부 삭제 후 중단되면 남은 항목에 경고 표시한다. 성공한 항목·중단·미처리를 나누며, 응답이 끊기면 삭제 여부 확인을 요구한다. 남은 항목은 다시 비밀번호 확인 후 처리할 수 있다. 폴더 복원은 남아 있는 파일만 복원할 수 있다.

성장 기록의 본문은 유지하며 삭제된 원본과 정확히 일치하는 사진 참조만 제거한다. 같은 경로에 새로 생긴 사진 참조는 유지한다. 고정 앨범 경로/대표사진 선택은 유지하므로 필요하면 다시 선택한다. 삭제는 파일시스템에서 제거하는 것이며 디스크 보안 덮어쓰기나 Synology 백업/스냅샷 삭제를 뜻하지 않는다.

로컬 임시 파일로 인증·선택 범위·변경 감지·재사용/만료·심볼릭 링크·중단 복구·기록 참조를 검증했다. 실제 NAS 검증은 버려도 되는 테스트 사진/폴더를 휴지통에 넣어 수행한다. 개발 과정에서는 실제 NAS 삭제를 실행하지 않았다.


## 갤러리 영상 지원

`downloads/our-story-video.zip`의 `server.py`로 기존 `/docker/our-story/hotfix/server.py`를 덮어쓰고 `our-story-api`만 재시작한다. 다른 패키지 설치나 이미지 교체는 필요 없다. 기존 로그인·터널·`ENABLE_WRITES=1`·`/photos:rw`·`/settings:rw`·파일 마운트 설정을 유지한다. 사이트 새로고침 후 영상 기능이 표시된다.

- 목록/관리: MP4, M4V, MOV, WebM 확장자의 원본을 사진과 함께 표시한다. 개별 이동·이름 변경·다중 선택·휴지통·복원·선택 영구삭제는 기존 안전 절차를 따른다. 홈/성장 자동 사진 앨범 및 성장 기록 사진 첨부는 영상과 섞지 않는다.
- 재생: HTML video 기본 컨트롤, 터치 전체화면, 구간 탐색을 사용한다. `/api/video`는 매 HTTP 요청에 Origin/현재 서버 세션/경로/파일 revision을 검사하고 200/206/416 및 단일 Range를 지원한다. 열린 끝 Range는 최대 8MiB 단위로 응답한다. 서버는 64KiB씩 전송하고 대용량 원본을 통째로 메모리에 올리지 않는다. 같은 파일이 바뀌면 거부/스트림 중단한다.
- 첫 장면: 화면 가까운 영상만 두 개씩 브라우저 video/canvas로 JPEG 미리보기를 만든다. NAS에 ffmpeg를 설치하거나 영상을 자동 변환하지 않는다. 실패하면 영상 아이콘을 유지하고 원본 재생/다운로드를 제공한다. MOV/HEVC 등 실제 재생과 첫 장면 지원은 기기·브라우저 코덱에 따라 달라진다.
- 인증 중계: HTTPS 서비스 워커가 해당 페이지 메모리에서 받은 인증을 NAS 요청의 Authorization 헤더에 붙인다. 재생 URL은 탭에 묶인 임의 핸들이며 비밀번호·세션·실제 파일 경로를 포함하지 않는다. 다른 탭의 핸들을 요청해도 거부한다. 워커가 종료되었다가 재시작되면 요청한 탭의 메모리에서만 연결을 다시 받는다. 로그인 만료/로그아웃 이후 새 범위 요청은 거부되며 이미 수신한 바이트를 지운다는 보장은 하지 않는다. 오프라인 캐시를 만들지 않는다. 서비스 워커를 사용할 수 없는 인앱 브라우저는 일반 Chrome/Safari에서 열도록 안내한다.
- 다운로드: `/api/video-download`의 인증된 원본 스트림을 같은 워커에서 브라우저 다운로드로 전달한다. 원본을 Blob 전체로 받지 않는다. 해당 탭을 닫거나 로그아웃하면 연결이 종료될 수 있다. 실제 브라우저의 다운로드 처리는 수동 확인 대상이다.
- 업로드: 영상당 최대 4GiB, 8MiB씩 전송하고 각 조각 SHA256/offset을 검증한다. `/settings/video-uploads.sqlite3`(0600)에 업로드 세션과 조각 영수증을 저장한다. 같은 로그인 세션/폴더/파일을 다시 선택하면 이미 받은 모든 조각의 해시를 브라우저 파일과 대조한 뒤 이어 올린다. 재시작 전후 불확실한 마지막 조각은 저장된 offset으로 되돌리고 재전송한다. 파일명·크기·처음/끝 지문은 검색 키이며, 이어 올릴 원본의 동일성 판단은 조각 해시 검증을 사용한다. 새 로그인 세션/다른 기기에서 기존 업로드를 인계하지 않는다.
- 공개 시점: 대상 폴더의 숨김 임시 파일에 쓰고 fsync 후 컨테이너 헤더를 확인한다. 전체 코덱/트랙 무결성 검사를 하는 것은 아니다. 완료된 파일만 no-clobber hardlink로 게시하며 기존 같은 이름/심볼릭 링크를 덮어쓰지 않는다. 완료 영수증을 남긴 뒤 임시 링크를 제거한다. 권한/용량/원본 폴더 identity가 바뀌면 거부한다. 중단된 파일은 목록에 표시하지 않는다.
- 임시 정리: 다음 업로드 시작 시 48시간 이상 갱신되지 않은 해당 서비스 임시 파일만 저장된 부모/파일 inode를 확인한 뒤 정리한다. 원본 파일은 정리하지 않는다. 활성 미완료 업로드는 세션당 32개/서버 전체 128개이며 NAS 여유 공간도 검사한다. 업로드 중인 폴더는 이동/삭제하지 않는다.

실기기 최소 확인: 버려도 되는 짧은 MP4 하나를 갤러리에서 첫 장면 → 재생/중간 탐색/전체화면 → 원본 다운로드 → 다른 이름으로 업로드 → 전송 창 닫고 같은 파일 다시 선택해 이어 올리기 순으로 확인한다. 미지원 코덱은 다운로드 안내가 나오는지 확인한다. 기존 사진도 한 장 열어 본다. 개발 테스트는 임시 로컬 파일과 워커 모의 요청만 사용했으며, 실제 NAS와 모바일 재생 검증을 완료했다고 주장하지 않는다.


## 서버에서 영상 썸네일 만들기

기존의 브라우저 첫 장면 방식은 해당 브라우저가 영상을 해독할 수 있어야 한다. 새 API가 `videoThumbnails:true`를 반환하면 갤러리는 `/api/video-thumbnail?path=...&revision=...`의 인증된 JPEG를 사용한다. 브라우저가 영상을 재생하지 못해도 서버가 해독할 수 있으면 썸네일을 표시한다. 모든 영상이 해독된다는 보장은 없으며, 실패하면 영상 아이콘/원본 다운로드를 유지한다. 새 ffmpeg가 없는 기존 서버는 브라우저 방식으로 동작한다.

ffmpeg는 이미지 빌드 시 Debian 패키지로 설치한다. 기존 컨테이너에는 아래의 별도 런타임 폴더만 추가할 수 있다. 임의의 바이너리를 NAS 시스템 경로에 설치하거나 기존 API 컨테이너를 삭제하지 않는다.

### 기존 Synology 컨테이너에 적용 (터미널 불필요)

1. `https://github.com/mashimaru7-max/mashimaru/releases/download/our-story-video-thumbnails/our-story-video-thumbnails.tar.gz`를 받는다. GitHub 로그인은 필요 없다.
2. `our-story-api`만 중지한다. 기존 `docker/our-story/hotfix/server.py`를 별도로 보관한 뒤, tar.gz의 **내용물**(server.py, bin, lib, licenses, INSTALL.txt)을 `docker/our-story/hotfix` 안에 푼다. bin/lib의 실행 권한을 보존하도록 tar.gz를 직접 압축 해제한다.
3. API 컨테이너 볼륨 설정에서 **폴더 추가**: `/docker/our-story/hotfix` → `/ffmpeg-runtime`, 읽기 전용 체크. 기존 hotfix 파일 → `/app/server.py` 매핑도 유지한다. bin/lib가 /ffmpeg-runtime/bin, /ffmpeg-runtime/lib 위치가 되어야 한다.
4. 기존 `/settings`·`/photos` 매핑, 사진 쓰기 설정, 사용자/네트워크/터널/로그인 설정을 유지하고 저장 후 API를 시작한다. 웹 새로고침 후 영상 폴더를 연다. 원복이 필요하면 API를 중지해 보관한 로그인 지원 server.py로 되돌리고 추가 폴더 매핑만 제거한다.

전체 ffmpeg 런타임은 약 100MB 규모이며 일회 설치다. `tools/package-ffmpeg.py`는 API 이미지에 설치된 ffmpeg와 ldd가 확인한 공유 라이브러리/로더를 묶고, 그 로더로 바이너리를 실행하는 검증을 수행한다. tar를 사용해 실행 권한을 유지한다. Debian의 저작권/라이선스와 패키지별 대응 소스 위치는 licenses에 동봉한다. 새 이미지와 기존 컨테이너용 런타임은 같은 워크플로에서 빌드한다.

### 처리와 제한

- 먼저 원본을 O_NOFOLLOW fd로 열고 현재 세션·Origin·경로·revision을 검증한다. 경로 문자열을 ffmpeg 명령으로 전달하지 않고 열린 fd만 상속한다. 하위 프로세스에는 NAS_TOKEN 등 서버 환경의 비밀을 전달하지 않는다.
- MP4/MOV 또는 WebM demuxer를 고정하고 MOV 외부 참조·네트워크 프로토콜을 허용하지 않는다. ffmpeg는 nice 10(지원 시), 소프트웨어 1스레드, 16,777,216 픽셀 제한, 20초 제한으로 실행한다. 원본을 변환/덮어쓰지 않고 첫 영상 프레임 하나를 최대 640×640 JPEG로 표준 출력에 만든다.
- 생성은 한 번에 하나이며 대기 요청 포함 최대 3개만 허용한다. 대기 상한 25초, 초과 시 429. 같은 원본 동시 요청은 잠금 후 캐시를 다시 확인해 한 번만 생성한다. 캐시가 있으면 디코더를 기다리지 않는다.
- JPEG는 `/settings/video-thumbnails/vt1-<revision>.jpg`에 0600, 디렉터리 0700으로 원자 저장한다. 최대 256MiB를 넘으면 오래 요청하지 않은 JPEG만 정리한다. 영상 원본은 정리하지 않는다. 생성 도중 원본이 바뀌면 결과를 폐기한다. 손상/시간 초과는 10분간 재시도를 억제한다.
- 브라우저는 사진과 같은 lazy JPEG 표시를 사용한다. 페이지 이탈/미리보기 끄기는 요청을 취소하고, 이미 시작한 서버의 짧은 생성은 마쳐 캐시할 수 있다. NAS 자체에 ffmpeg를 설치하거나 영상 자동 트랜스코딩을 하지 않는다.

임시 H.264/HEVC 영상으로 JPEG 생성·원본 보존·캐시 재사용·재시작 재사용·동시 요청 단일 생성·인증/경로/변경/손상/시간 초과를 검사한다. 포터블 로더/라이브러리 묶음에서도 HEVC→JPEG를 실제 실행한다. 실제 Synology 폴더 권한과 사용자 영상의 썸네일은 설치 후 사용자 확인 대상이다.


## 브라우저 다운로드 관리자 호환 수정

`downloads/our-story-video-download-fix.zip`의 server.py만 기존 hotfix에 교체하고 API를 재시작한다. ffmpeg의 bin/lib와 기존 볼륨 매핑은 그대로 둔다. 실패한 브라우저 다운로드 기록의 재시작 대신 웹에서 원본 다운로드 버튼을 다시 누른다.

서비스 워커의 가상 재생 URL은 브라우저 다운로드 관리자에서 페이지 clientId/워커 실행 여부가 달라 실패할 수 있다. 다운로드 버튼은 인증된 `POST /api/video-download-ticket`으로 파일 경로/revision을 검증해 티켓을 얻은 뒤, 실제 NAS `GET /api/video-file/<ticket>`을 연다. 가족 비밀번호·로그인 세션은 URL에 넣지 않는다. 임의 256비트 티켓은 해당 파일에만 한정하고 2분 이내 다운로드를 시작해야 하며 성공적인 GET 시도 한 번에 소비한다. 발급 세션이 만료/로그아웃되면 사용할 수 없다. HEAD는 파일 헤더만 반환하고 티켓을 소비하지 않는다. GET은 재개 Range를 무시하고 원본 전체를 스트리밍하므로, 전송 실패 시 웹 버튼에서 새 링크를 받아야 한다.

직접 다운로드 요청은 Origin/Authorization이 없어도 티켓과 현재 세션/파일 revision을 검증한다. Origin이 제공되면 가족 웹사이트와 일치해야 한다. 진행 중에도 10초마다 세션을 재검사하고 파일 변경 시 연결을 끊는다. 스트림 시작 후에는 2분을 넘겨도 진행할 수 있다. Cache-Control:no-store, Referrer-Policy:no-referrer, 첨부 파일명과 CSP sandbox allow-downloads를 사용한다. 본문은 64KiB 단위로 흘려 보내고 대용량을 브라우저 Blob 메모리에 올리지 않는다. API 재시작 시 미사용 티켓도 폐기한다. 로그에 티켓을 남기지 않는다.


## 실제 가족 여행기·지도·버킷리스트

`downloads/our-story-travel.zip`의 server.py를 기존 hotfix에 교체하고 API만 재시작한다. ffmpeg bin/lib, 기존 볼륨/터널/로그인 설정은 유지한다. 새 기록은 `/settings/travel.sqlite3`(0600)에 저장한다. 여행 기록은 사진 읽기 전용 환경에서도 저장할 수 있으며, NAS 원본을 이동/삭제하는 기능과 별개다.

로그인한 여행 화면의 ‘여행 남기기’에서 제목, 국내/해외, 국가/도시, 날짜, 동행 가족, 지도 위치, 작성자 표시와 이야기를 적는다. 지도 클릭 또는 ‘지도 가운데 위치 선택’으로 위치를 직접 정한다. 좌표를 고르지 않으면 (0,0) 같은 임의 위치로 저장하지 않는다. 장소 검색·역지오코딩·EXIF GPS 자동 분류는 구현하지 않았다. 공용 로그인 아래의 작성자/가족 한마디는 사용자가 선택한 표시이며 개별 계정 감사 기록은 아니다.

여행별 폴더를 한 번 연결하면 하위 사진을 영구 공통 색인으로 모아 최대 12장 미리보기를 표시한다. 색인 진행 중에는 자동으로 이어 확인하며, 전체 사진·영상은 해당 폴더의 기존 갤러리로 연결한다. 대표 미리보기는 현재 방문의 고정 시드로 골라 보여주며 원본을 복사/재정리하지 않는다. 영상은 전체 갤러리에서 기존 썸네일/재생/다운로드/관리 기능을 사용한다. 연결 폴더가 바뀐 기록의 오래된 상세 화면은 revision 검사로 새 폴더 사진과 섞지 않는다.

지도에는 저장한 여행 위치만 표시한다. 세계/국내, 연도, 검색과 여행 목록은 같은 실제 기록을 사용한다. 지도는 필터 범위 최근 2,000개 위치까지, 목록은 20개씩 더 보기로 제공한다. 통계는 필터와 별개로 휴지통을 제외한 전체 여행의 횟수/국가/도시 및 미완료 버킷리스트 수다. 국내 국가 표기는 대한민국으로 통일한다. 홈의 최근 여행도 같은 DB를 읽는다. 예시 통계를 실제 기록처럼 쓰지 않는다.

버킷리스트는 여행기와 다른 양식(시기·하고 싶은 일·완료 표시)으로 저장한다. 완료 체크만으로 다녀온 여행 통계나 핀을 만들지 않는다. ‘이곳의 여행기 남기기’는 별도 새 여행 양식을 열고 실제 날짜/위치를 선택하도록 한다. 기록 수정·휴지통·복원은 UUID/revision CAS와 생성 재시도 중복 방지를 사용한다. 여행기의 삭제는 이야기 DB의 휴지통 표시만 바꾸며 NAS 원본을 지우지 않는다. 실제 가족 여행을 예시 데이터나 localStorage에 넣지 않는다.

갤러리에서 여행 폴더를 이동/이름 변경할 때 FileManager가 여행 DB의 관련 폴더와 revision도 갱신한다. 이동 전 계획에는 경로/기록 해시만 남기고 이야기 본문은 복제하지 않는다. 이동 후 중단되면 다음 인증된 메타데이터 요청에서 멱등 복구한다. 복구 충돌은 덮어쓰지 않고 503으로 막는다. 여행 DB는 기존 성장 기록 DB와 별개이므로 성장 기록 백업 버튼에는 포함되지 않는다. API를 중지한 상태의 /settings 전체 백업에 포함한다. 여행 전용 내보내기/복원 UI, 성장 기록과 여행 ID 연결은 다음 단계다.

API는 `/api/travel`의 GET 목록/단건·POST 저장/휴지통/복원, `/api/travel-album`의 POST 폴더 사진 조회다. 가족 로그인 세션과 Origin을 서버에서 검사한다. 날짜/유한 좌표/가족/본문 길이/폴더 경계를 검증하고 경로 순회/심볼릭 링크 폴더를 거부한다. 최대 10,000개 기록, 가족 한마디당 2,000자·이야기 8,000자, 지도 핀 2,000개 제한을 둔다. 입력 오류/충돌 때 클라이언트는 작성 중 양식을 유지하며 저장 성공으로 표시하지 않는다. 로그아웃/세션 만료 시 개인 DOM/이미지를 정리한다.

검증은 임시 데이터의 CRUD·재시작·충돌·휴지통/복원·통계/필터·인증·실제 폴더 색인 및 폴더 이동 중단 복구로 수행한다. 실제 모바일 지도 조작과 NAS 여행 등록은 사용자 확인 대상이다. 설치 후 테스트 여행 하나로 지도 위치 선택 → 사진 폴더 연결 → 저장 → 다른 기기에서 확인 순으로 점검한다.


## 확대 화면의 촬영 날짜·위치 / 갤러리 사진·영상 필터

웹의 전체/사진/영상 필터는 서버 업데이트 없이 사용한다. 폴더는 모든 필터에서 탐색할 수 있도록 남긴다. 필터는 현재 불러온 목록에 적용되며 뒤 페이지는 기존 더 보기/스크롤 로딩으로 계속 조회한다. 선택 전체는 표시된 필터 범위만 포함하고 필터를 바꾸면 이전 선택을 해제한다.

`downloads/our-story-media-info.zip`의 server.py를 기존 hotfix에 교체하고 API를 재시작하면 촬영정보를 읽는다. 기존 ffmpeg 폴더와 마운트를 유지하며 새 프로그램 설치는 없다. 이 파일에는 앞선 여행 저장과 영상 다운로드 수정도 포함한다.

`GET /api/media-info?path=...&revision=...`는 현재 세션/Origin/사진 경로와 revision을 확인한 후 원본을 읽기 전용으로 연다. Pillow의 EXIF DateTimeOriginal과 GPS IFD만 해석하고 생성/수정일을 촬영일로 바꾸지 않는다. EXIF 달력 날짜는 원본에 쓰인 값 그대로 표시하며 임의의 시간대 변환을 하지 않는다. 읽기 전후 revision이 달라지면 409로 거부한다. HEIC 등 현재 Pillow가 해독하지 못하는 형식/잘린 EXIF에는 미확인으로 응답하며 원본을 바꾸지 않는다. GPS·촬영일을 별도 DB에 색인하거나 브라우저에 영구 저장하지 않는다.

원본 날짜가 없거나 구형 API이면 `2024/1월 ...` 같은 폴더의 명시적 연도/월을 ‘폴더 이름 기준 · 촬영일과 다를 수 있음’으로 구분한다. 파일명 숫자/수정일을 촬영일로 추측하지 않는다. 영상 생성일의 컨테이너 메타데이터는 아직 읽지 않으므로 영상은 해당 폴더 기준 또는 미확인으로 표시한다.

GPS가 있으면 사용자가 누를 때 OpenStreetMap 지도 링크를 연다. 서버가 좌표를 외부 역지오코딩 서비스로 전송하지 않는다. 지역명은 실제 여행 기록에서 해당 파일의 폴더를 연결한 경우에만 가져오고 ‘연결한 여행의 지역’이라고 표시한다. 가장 구체적으로 연결된 하위 폴더를 우선하며 같은 폴더의 연결 여행은 최대 3개까지 보인다. 실제 촬영 위치로 단정하지 않는다. GPS/여행 연결이 없으면 위치 미확인으로 표시한다.
